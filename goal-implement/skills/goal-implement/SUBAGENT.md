# Sonnet サブエージェント指示テンプレート

実装・テスト・修正作業はすべて Task ツールのサブエージェント（`model: sonnet`）に委譲する。サブエージェントは run の文脈を持たないため、**毎回必要な情報を完結に渡す**こと。返答には「変更ファイル一覧・実行したテストコマンドと結果・自己評価（懸念があれば明記）」を必ず含めさせる。

## 共通フッター（全テンプレートに付ける）

```
## 報告形式（必須）
- 変更ファイル一覧（パスと変更概要）
- 実行したテストコマンドと結果（成功/失敗の生出力サマリ）
- 自己評価: 懸念・未対応事項があれば正直に列挙（なければ「なし」）
- 指示範囲外の変更はしない。必要だと気づいたら変更せずに報告する
```

## テストワーカー（P4 Red）

```
あなたは TDD のテストファーストを担当するエンジニアです。実装はまだ書かず、テストのみ作成してください。

## 対象機能
<機能 F<n> の説明>

## 対応する要件
<要件 R<x> の内容>

## テスト観点（設計書より）
<設計書のテスト観点>

## プロジェクト情報
- テストコマンド: <test_commands>
- テスト配置規約: <プロジェクトの規約・既存テストの例>

## 実施事項
1. 上記観点を網羅するテストを作成する（境界値・異常系を含める）
2. テストを実行し、実装が無いことにより失敗することを確認する（失敗の仕方が期待どおりかも確認）
3. 失敗出力を報告に含める

<共通フッター>
```

## 実装ワーカー（P4 Green + Refactor）

```
あなたは TDD の実装を担当するエンジニアです。既存のテストを通すことがゴールです。

## 対象機能
<機能 F<n> の説明と対応要件>

## テストファイル
<テストファイルパス>

## 実施事項
1. Green: テストを通す最小実装を書く。テストは変更しない（テスト自体の欠陥を見つけたら変更せず報告する）
2. Refactor: テストを green に保ったまま、重複排除・命名改善・構造整理を行う
3. 最終的に全テスト（既存含む）が通ることを確認する: <test_commands>

<共通フッター>
```

## 修正ワーカー（P4/P6 レビュー指摘対応）

```
あなたはレビュー指摘の修正を担当するエンジニアです。以下の指摘のみを修正してください。

## レビュー指摘（構造化形式）
<findings JSON のうち、採用された open の指摘のみ>

## 実施事項
1. 各指摘の required_fix に従って修正する
2. 修正ごとに対応する finding の ID を報告に紐づける
3. 全テストが通ることを確認する: <test_commands>
4. required_fix に同意できない・実行不能な場合は、その指摘は修正せず理由を報告する

<共通フッター>
```

## CI 修正ワーカー（P7）

```
あなたは CI 失敗の修正を担当するエンジニアです。

## 失敗した CI ジョブとログ
<gh run view --log-failed の抜粋（失敗箇所中心）>

## 今回の PR の変更内容
<変更ファイル一覧と概要>

## 実施事項
1. 失敗原因を特定し、今回の変更に起因する問題を修正する
2. ローカルで再現・確認できる場合は確認する: <test_commands / lint コマンド>
3. 変更起因でないと判断した場合は、修正せず根拠を報告する

<共通フッター>
```

## 受領後のオーケストレーター側チェック

- 報告の「自己評価」に懸念が書かれていたら、無視せず対応（修正再依頼 or レビューで確認）する
- テスト結果サマリを `<run-dir>/test-results/<feature>-<連番>.md` に保存する
- サブエージェントが「テストを変更した」と報告した場合は diff を確認する（Green でのテスト改変は原則禁止）
