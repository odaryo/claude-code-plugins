bp-audit で作成した改善計画に基づいて、設定を改善してください。

## Phase 1: 事前チェック

1. `git status` を実行し、作業ツリーの状態を確認
2. 未コミットの変更がある場合:
   - 「未コミットの変更があります。改善適用前にコミットすることを推奨します。続行しますか？」とユーザーに確認
   - ユーザーが中止を選択した場合は終了

## Phase 2: 改善計画の読み込み

1. `$ARGUMENTS` でパスが指定されている場合はそのファイルを読み込み
2. 指定がない場合、`.ai/setting_reports/*/*/bp-plan*.md` を Glob で検索
3. 各ファイルの frontmatter から `created_at` を読み取り、最新のファイルを選択
4. frontmatter がないファイルはディレクトリ名から日付を復元（フォールバック）
5. 計画が見つからない場合は「先に `/bp-audit` を実行してください」と案内

計画を読み込んだら、アクション一覧をユーザーに表示:
```
改善計画: {計画ファイルパス}
アクション数: N件

[P1] {タイトル} — {対象ファイル}
[P2] {タイトル} — {対象ファイル}
...

優先度順に1件ずつ適用します。各変更は個別に確認を取ります。
```

## Phase 3: アクションの適用

優先度順（P1 → P2 → ...）に各アクションを処理:

### 3a. 対象の妥当性チェックと変更内容の表示

適用前に各アクションを検証する（計画は過去に作成されたものであり、現状と乖離している可能性がある）:
- **パス境界:** 対象ファイルがリポジトリ内にあること。リポジトリ外（`~/.claude/` 等）への変更は「参考提案」の追加確認フロー以外では適用しない。symlink の場合は解決先もリポジトリ内であることを確認
- **現状との一致:** 計画の「現状」欄と実際のファイル内容が一致するか確認。乖離している場合（計画作成後に変更された等）はその旨を表示し、変更内容を現状に合わせて調整するかユーザーに確認
- **内容の安全性:** 変更内容に機密情報や危険なコマンド（後述の安全ルール参照）が含まれていないか確認

対象ファイルが存在する場合:
- ファイルの該当部分を読み込み
- before/after の diff 形式で変更内容を表示

対象ファイルが存在しない場合（新規作成）:
- 作成するファイルの全内容を表示

### 3b. ユーザー確認

「この変更を適用しますか？」とユーザーに確認。選択肢:
- **適用する** → 3c へ
- **スキップ** → 次のアクションへ
- **変更内容を修正して適用** → ユーザーの修正指示を受けて調整後に適用
- **残り全てスキップ** → Phase 4 へ

### 3c. 変更の適用

- 既存ファイルの変更: **適用前にファイルのバックアップを保存してから** Edit ツールを使用。バックアップ先は今回の実行ディレクトリ `.ai/setting_reports/{YYYY_MM}/{DD}/bp-applied-backup/`（結果レポートが連番付きなら `bp-applied-backup-2/` のように対応させ、過去の実行のバックアップを上書きしない）配下の `{アクション番号}_{ファイル名}`。適用結果の表にパスを記録する（これがあれば後日でも確実にロールバックできる）
  - **機密漏えい防止:** バックアップには `settings.local.json` 等の機密を含み得るファイルの完全コピーが入るため、`.gitignore` に `.ai/setting_reports/**/bp-applied-backup*/` が含まれることを確認し、なければ追加する。この追記は**最初のアクションのユーザー確認（3b）の際に併せて提示**し、同意とともに適用する（「各変更は必ず確認を経る」の原則と整合させるため）。結果レポートにはバックアップの内容を転記せず、パスのみ記録する
- 新規ファイルの作成: Write ツールを使用（バックアップ不要。結果表に「新規作成」と記録）
- `.gitignore` へのエントリ追加: 既存内容に追記

### 3d. 検証

適用後:
1. ファイルを Read で読み戻し、変更が正しく反映されているか確認
2. JSON ファイル（settings.json 等）の場合は `jq .` で構文検証
3. `shasum -a 256` で適用後のハッシュを取得し、結果表に記録（後日のロールバック時に、適用後にユーザーが変更を加えていないか判定するため）
4. 問題があれば即座にユーザーに報告

### 安全ルール（厳守）

- **APIキーやトークンの値そのものを設定ファイルに書き込まない**
- **破壊的コマンド（`rm -rf`, `git push --force` 等）を実行しない**
- **グローバル設定（`~/.claude/settings.json`）への変更は「参考提案」セクションのものに限り、追加の確認を取る**
- **各変更は必ずユーザー確認を経てから適用する**

## Phase 4: 適用結果の保存

```markdown
---
type: bp-applied
created_at: {ISO 8601 datetime}
based_on_plan: {bp-plan.md のパス}
claude_code_version: {claude --version の出力}
tool_version: "1.0.0"
---

# Claude Code 改善適用結果
日付: {YYYY-MM-DD}
改善計画: {bp-plan.md のパス}

## 適用結果

| # | アクション | 状態 | 対象ファイル | 種別 | バックアップ | 適用後ハッシュ | 備考 |
|---|-----------|------|------------|------|------------|--------------|------|
| P1 | {タイトル} | 適用済み | {path} | 変更 | {backup path} | {sha256 先頭12桁} | |
| P2 | {タイトル} | スキップ | {path} | - | - | - | ユーザー判断 |
| P3 | {タイトル} | 修正適用 | {path} | 新規作成 | - | {sha256 先頭12桁} | {修正内容} |

## 適用済み変更のロールバック手順
ファイルの種別ごとに手順が異なります（`git checkout -- {file}` は適用前からあった未コミット変更ごと戻してしまうため使わない）:
- **共通の事前確認**: 復元前に `shasum -a 256 {file}` を結果表の「適用後ハッシュ」と比較してください。異なる場合は適用後にユーザーが変更を加えています。そのまま復元するとその変更も消えるため、警告して確認を取ってから実行します
- **変更したファイル**: 3c で保存したバックアップから復元します: `cp -- "{backup path}" "{file}"`
- **新規作成したファイル**: このスキルが作成したものであることを確認した上で `rm -- "{file}"` で削除します
- **同一ファイルに複数アクションを適用した場合**: 各アクションのバックアップは「そのアクション適用直前」の状態です。全アクションを戻す場合は**最初の**アクションのバックアップを復元します。一部だけ戻す場合は適用順の逆順で戻してください（途中のアクションだけ戻すと後続の変更も消えるため、その場合は影響をユーザーに説明する）

- 新しいベストプラクティスを調査する場合は `/bp-research` を実行
```
